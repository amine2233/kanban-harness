:::note Design note
Where a log line goes, what may never be in one, and who turns the machinery on — after the daemon made stderr disappear. Source: `docs/conceptions/logging.md`.
:::

The daemon changed what a log is for. Every process used to be short-lived with its stderr in
front of you; now one background process owns the data for days and **its stderr goes to
`/dev/null`** — `DaemonProcess.spawnUnlessAnotherIsStarting` sets
`standardError = FileHandle.nullDevice`. Whatever it says is discarded as it is said.

That is why [`daemon.md`](../daemon) § _When something is wrong_ can only
offer one answer to every failure: run `dashboard daemon run` in the foreground and make it
happen again. A daemon that cannot be asked what it did is a daemon that can only be
reproduced.

This note decides where a log line goes, what may never be in one, and who turns the machinery
on. It does not decide which lines get written — that is the companion card, and it needs this
one first.

## Today

|                                        |                                                                                                                                                         |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| swift-log                              | a dependency; `Logger(label: "dashboard")` behind `@Dependency(\.logger)` ([R-07](https://github.com/amine2233/kanban-harness/blob/main/docs/RULES.md)) |
| `LoggingSystem.bootstrap`              | called nowhere — so the default handler writes to stdout                                                                                                |
| `logger.*` call sites under `Sources/` | two                                                                                                                                                     |
| the daemon's stderr                    | `/dev/null`                                                                                                                                             |
| what a user sees                       | `Output.swift`: JSON on stdout, narration on stderr — a product contract, not logging                                                                   |

The last row is the one to keep straight. `Output.swift` is what a command _answers_; logging is
what the system _remembers_. They share a stream today and must not share a fate: a log file
that swallowed stdout would break every script piping `dashboard project list` into `jq`.

## Decisions

### D-1 — the handler is the extension point; there is no logging service

**Decision.** Write a `LogHandler`. Do not write a service that wraps `Logger`.

swift-log is already built around exactly one seam — `LoggingSystem.bootstrap` installs a
`LogHandler` factory, and every `Logger` in the process goes through it. `@Dependency(\.logger)`
already supplies the logger to call sites, so injection is solved too. A `LoggingService` on top
would be a second abstraction over the one the library provides, and every call site would have
to learn it to gain nothing.

The measure of this decision: **no call site changes.** Lines that log today land in the file
because the handler under them changed, not because they were rewritten.

**Rejected.** A `LoggingService` registered in the container beside the other services. It looks
consistent with `DashboardRuntime.register`, and it is the reason to say no — consistency with
the container is not a reason to duplicate a library's own design.

### D-2 — one file, in the home

**Decision.** `home/dashboard.log`, created `0600`.

The home already holds everything that belongs to one owner — `projects.sqlite`,
`settings.json`, `credentials.json`, `daemon.port` — and two homes never share a daemon, so two
homes must not share a log either. Putting it anywhere else invents a second notion of "which
dashboard is this".

`0600` because of D-5: the file will contain enough to reconstruct what someone did, on a
machine where `credentials.json` is already written `0600` for weaker reasons.

**Rejected.** A system location (`~/Library/Logs`, `/var/log`). Correct for a daemon a package
manager installed; wrong for one that a `cd` into a folder can start, where the per-home
isolation is the whole point.

### D-3 — bootstrap once, in the process that owns the home

**Decision.** `LoggingSystem.bootstrap` is called in `DaemonCommand.Run` and `ServeCommand` —
the two processes that take a home — and nowhere else. It installs
`MultiplexLogHandler([FileLogHandler, StreamLogHandler.standardError])`.

A one-shot command lives about forty milliseconds and does its work through the daemon; what it
did is already in the daemon's file. Bootstrapping it too would mean every `dashboard project
list` opens and rotates a log file for one line.

**The two handlers do not share a level.** This is the part that decides whether the feature
works at all.

| Handler | Level             | Why                                       |
| ------- | ----------------- | ----------------------------------------- |
| file    | `.debug`          | the file is the record; it should be full |
| stderr  | `global.logLevel` | the terminal stays as quiet as today      |

`MultiplexLogHandler` forwards only to handlers whose own `logLevel` admits the message and
reports the minimum as its own, so per-handler thresholds are what it is for. Give the file the
same level as stderr and the file is empty in normal operation — the whole note delivers nothing.

**Three traps, all load-bearing.**

1. `LoggingSystem.bootstrap` may be called **once per process**; a second call traps. Anything
   that builds a runtime in-process — the test targets do — must not reach it. Bootstrap from the
   command, not from `DashboardRuntime.register`.
2. It must run **before the first `Logger` exists**, which means before `Vapor.Application.make`.
   A handler installed after a logger was created does not reach that logger. Verify where
   `app.logger` takes its handler from before settling the call site.
3. [`Runtime.swift:45`](https://github.com/amine2233/kanban-harness/blob/main/Sources/DashboardCLI/Runtime.swift) sets
   `$0.logger.logLevel = global.logLevel`. That is the **Logger's** level: it drops a `debug`
   record before the multiplex ever sees it, so the file never receives one. Set the stderr
   handler's level instead and leave the logger at the multiplex minimum. One line, and the
   difference between a working log file and an empty one.

### D-4 — rotation by size, one file kept

**Decision.** At 5 MB, rename to `dashboard.log.1` and start a new file. One old file kept.

A daemon that runs until the machine restarts writes forever, and an unbounded file in the home
is a bug with a slow fuse. Size is the honest trigger: a daemon that idles for a week should not
rotate, and one that thrashes in an hour should.

**Rejected.** Date rotation, and `logrotate`. The first rotates on a schedule unrelated to
whether anything happened; the second is a second tool, configured elsewhere, absent on the
machine of whoever hits the bug.

_ponytail: rotate on write when the size is already known. A count and a timestamp per line is
all the format needs; structured JSON lines if anything ever parses them._

### D-5 — what may never be written

**Decision.** [R-23](https://github.com/amine2233/kanban-harness/blob/main/docs/RULES.md) already says never log a secret. The file makes it sharper,
because a terminal forgets and a file does not. Specifically out, at every level including
`debug`:

- API keys and OAuth tokens, whole or partial — a prefix identifies the key as surely as the key.
- `Authorization` headers, and any header dump that could carry one.
- the contents of `credentials.json`, and any error string built from them.
- request and response bodies from providers, which carry the card text a user typed.

In, and worth the line: provider **id and kind**, model name, latency, token counts, HTTP status.

The test for a new log statement is not "is this a secret" but "would I paste this file into an
issue". If the answer needs thinking about, the line is wrong.

### D-6 — levels mean something

**Decision.** Five of swift-log's seven levels are used, each with one meaning and a named place
in this codebase to look at when in doubt.

**`error` — something was lost and the user will notice.**
[`ApiErrorMiddleware.swift:16`](https://github.com/amine2233/kanban-harness/blob/main/Sources/DashboardServer/ApiErrorMiddleware.swift) already
has the right instinct: it reports **only** when the status is `500`. Also a save that fails after
the domain operation succeeded, a provider call that failed for real, and the daemon failing to
bind or migrate before it withdraws.

_Not_ `404`, `409` or `400`. Those are the caller being wrong, not the system failing, and they
are already the response. An error log that is nine parts "unknown column id" is an error log
nobody opens.

**`warning` — recovered, but someone should know.** Every one of these is a place the system
papers over something real today:

| Site                                                                                                                                 | What it hides                                               |
| ------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------- |
| [`DaemonProcess.swift:69`](https://github.com/amine2233/kanban-harness/blob/main/Sources/DashboardCLI/DaemonProcess.swift)           | a stale `daemon.lock` removed — a spawner died mid-start    |
| [`DaemonHandover.swift:35`](https://github.com/amine2233/kanban-harness/blob/main/Sources/DashboardCLI/DaemonHandover.swift)         | a `daemon.port` with nothing behind it — an owner crashed   |
| [`DashboardRuntime.swift:43`](https://github.com/amine2233/kanban-harness/blob/main/Sources/DashboardRuntime/DashboardRuntime.swift) | a typo in `config.yaml` silently becomes `DatabaseConfig()` |
| the build-mismatch path                                                                                                              | a daemon from another build evicted                         |

**`notice` — unused.** `--verbose` selects between `warning` and `info`; a third band between
them that no flag can reach is decoration. Wanting it is a different change — `--log-level
<level>` instead of `--verbose` — and should be decided once rather than discovered half-used.

**`info` — a state change someone would ask about later.** The backbone of the file, and only
these five:

- daemon lifecycle — started, bound port and pid, stopping, handing the home to pid X. Once
  `daemon.port` is gone nothing else records who owned the home at 14:02.
- every mutation, through `ProjectService.mutate` — the single funnel, so one statement rather
  than fifty.
- a provider call that completed: provider id, model, milliseconds, token counts. It costs money
  and today leaves no trace.
- a storage conversion, json ↔ sqlite.
- migrations run.

**`debug` — the flow, for reproducing a bug.** Both existing call sites are already exactly right
and are the model: [`Runtime.swift:32`](https://github.com/amine2233/kanban-harness/blob/main/Sources/DashboardCLI/Runtime.swift) (which daemon a
command bound to) and
[`EventsController.swift:24`](https://github.com/amine2233/kanban-harness/blob/main/Sources/DashboardServer/Routes/EventsController.swift) (an
events client disconnected). Add the HTTP line — method, path, status, ms — MCP tool name and
duration, and socket subscribe/unsubscribe.

**`trace` and `critical` — unused.** Nothing here needs a band below `debug`, and nothing here
dies in a way that loses data. An unused band invites someone to invent a meaning for it.

### D-7 — a `try?` is silent unless its failure would be invisible

There are 41 `try?` sites under `Sources/`. The test for each is one question: **if this fails,
will the next symptom point back here?**

1. **Cleanup on a path that is already failing** — `try? await app.asyncShutdown()` inside a
   `catch`, `defer { try? removeItem(lock) }`. **Silent.** A cleanup failure logged next to the
   real failure buries the real one.
2. **Absence is a legitimate answer** — `RuntimeConfig.daemonHandle` reading a `daemon.port` that
   is not there. **Silent**; it is not an error, it is "no daemon". That deserves a comment, not
   a log line.
3. **Failure changes behaviour and says nothing** — the `warning` table above. **Always logged.**

The 41 are worth grepping out once and sorting into these three, because group 3 is where the
next unexplainable bug is already waiting.

### D-8 — ids go in metadata, not in the message

`logger.info("card moved", metadata: ["card_id": .string(id.uuidString)])`, never string
interpolation. The file exists to be `grep`ed, and a stable key is what makes that work. It also
keeps [R-23](https://github.com/amine2233/kanban-harness/blob/main/docs/RULES.md) checkable: a reviewer can see which values reach a line.

## Implementation

Four patches. Each one stands alone, and the first two are the whole of the card
_Logs land in a file_; the fourth belongs to _Log at the boundaries that pay_.

**[1/4] `FileLogHandler` — the handler, no wiring.**
New file in `DashboardService`, beside `Dependencies.swift`, since that is where `LoggerKey`
lives and the target every other module already sees.

```swift
public struct FileLogHandler: LogHandler {
    public var logLevel: Logger.Level = .info
    public var metadata: Logger.Metadata = [:]
    public subscript(metadataKey key: String) -> Logger.Metadata.Value? { get set }

    public init(label: String, path: String, rotateAt bytes: Int = 5 * 1024 * 1024)
    public func log(level:message:metadata:source:file:function:line:)
}
```

One descriptor opened on init with `O_APPEND|O_CREAT` and mode `0600`; one lock around write and
rotation, since `LogHandler` must be `Sendable` and several tasks log at once. Rotation checked
on write against the size the handler already tracks — no `stat` per line.
_Check: a unit test writing N lines past the threshold, asserting two files and that the newest
line is in the live one._

**[2/4] Bootstrap in the two owners.**
`DaemonCommand.Run` and `ServeCommand`, before `Vapor.Application.make`, guarded so a second
call in one process is impossible. Level from `global.logLevel`.
_Check: a CLI test running a command, then asserting the daemon's line is in `home/dashboard.log`
and the file is `0600`. This is the test that proves D-1 — it passes without any call site having
changed._

**[3/4] Stop discarding the daemon's stderr.**
`DaemonProcess` sends the child's stderr to `/dev/null`. With [2/4] the same lines are in the
file, so this is not a data loss any more — but the `nullDevice` line should say that, or the
next reader will assume the daemon is silent by accident rather than by design.
_Check: none; it is a comment. It is here so it is not forgotten._

**[4/4] The statements.**
Companion card. Daemon lifecycle, `ProjectService.mutate` as the single mutation funnel, provider
calls, and the `try?` / `catch {}` sites where an error currently vanishes.

## Not in this note

- **Which lines get written** — patch [4/4] and its card. This note only guarantees they land
  somewhere.
- **`Output.swift`** — what a command answers is a product contract, decided by
  [`PRD.md`](https://github.com/amine2233/kanban-harness/blob/main/docs/PRD.md) CLI-01, and it does not move into the log.
- **Shipping logs anywhere** — no syslog, no collector, no remote sink. One file on one machine.
- **The web app's console** — a different process on a different machine.

## Open questions

- **Does anything read the file back?** `dashboard daemon status` could tail it, and
  `T-06` already wants pid, uptime and clients from that command. If it does, the format stops
  being free and becomes an interface.
- **Retention.** One rotated file is a guess. A daemon that has run since the last reboot may be
  the only witness to a bug from three days ago.
